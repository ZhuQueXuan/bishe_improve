# 上下文与自动记忆的内部化改造建议

日期：2026-10-24。状态：源码核对、官方资料调研与建议，尚未实施。用户希望记忆主要作为内部执行逻辑，自然生效，减少明显功能入口及提示。本轮未修改运行代码、数据库、页面或调用项目模型；没有操作Docker。

后续用户批准按顺序实施，当前已完成[28内部改造](28_过程_内部自动记忆与会话上下文改造.md)的有限版本。摘要采用原文摘取、自动记忆仍为有限值；真实模型试验待外发授权。健康记忆时效与相关性按用户要求留待实施后讨论，下文不能全部视为已实现。

## 现在实际有哪些能力

| 部分 | 当前实现 | 尚缺什么 |
| --- | --- | --- |
| 聊天原文保存 | 登录会话按账号保存消息；游客在当前页面保留 | 保存原文不等于模型能看到、理解和使用全部历史 |
| 短期状态 | 从当前会话用户消息重建疾病对象、预防限定、表格要求；记录来源、取消、更正与话题变化 | 有限语法，不是通用对话语义；没有最近完整对话片段和长历史摘要 |
| 回答上下文 | 当前问题、有效结构状态和当次医学证据；正式ChatAgent给最终回答模型的conversation_history为空 | 助手上一轮的组织方式没有直接传回，可能难以理解“刚才第二点”“把那个比较继续说” |
| 长期记忆 | 手动保存解释方式、篇幅、学习背景；按账号跨会话读取，最多3条，支持版本/停用/忘记 | 没有从自然对话自动形成记忆，没有自由文本历史回忆 |
| 预算与失效 | 状态12000字节、整体问题/上下文24000字节；重置有消息边界，登录恢复令牌绑定版本 | 当前超限主要停止，没有先压缩再继续的完整流程；UTF-8字节保护不等于精确token核算 |
| 当前界面 | 顶部记忆管理按钮、实时回答的使用记录 | 用户认为过于显眼，应调整为次级设置/可选审计 |

证据入口：`api/conversation_context.py`、`api/chat_runtime.py`的prepare_context与answer、`api/user_memory.py`、`api/views.py`以及`MemoryManager.vue`。已有316项后端及独立接口/页面验证见[26](26_过程_用户记忆管理第一版.md)，本次没有重复运行它们，也不能用原检查数证明尚未实现的自动记忆效果。

短期和长期主要区别是作用范围。一个会话的状态可保存很久，仍属于该会话；跨会话使用的用户信息才属于这里的长期记忆。上下文管理则决定每次调用模型时，从问题、历史、记忆和知识证据中挑哪些内容、用多少空间。

## 官方公开设计可借鉴什么

这里选择有代表性的框架和产品公开机制，不作市场排名，也不声称它们采用同一算法。

- **LangChain / LangGraph**：会话状态与跨会话store分开，长期记忆可同步写入或后台更新；历史可以裁剪、摘要或自定义筛选。借鉴其生命周期和分层，不需要为本项目迁移框架。[官方记忆概览](https://docs.langchain.com/oss/python/concepts/memory)、[短期记忆](https://docs.langchain.com/oss/python/langchain/short-term-memory)。
- **Google ADK**：配置MemoryService后，可通过preload自动读取或load_memory按需查找，通过回调接写入；上下文压缩可保留近期交互并压缩旧事件。这些机制需要应用配置，接上框架不等于自动具备完整记忆。[官方记忆](https://adk.dev/sessions/memory/)、[上下文压缩](https://adk.dev/context/compaction/)。
- **Claude Code**：会从纠正和偏好中选择值得以后使用的内容，保存为auto memory，详情按需读；也保留/memory供查看、编辑和关闭。它是编程产品，项目经验与本项目的用户健康信息性质不同，不能直接照搬范围。[官方auto memory](https://code.claude.com/docs/en/memory)。
- **Anthropic上下文工程说明**：讨论按需取上下文、压缩和结构笔记，强调选择有效信息；压缩过度可能丢掉重要细节。可借鉴机制，不能由此保证我们的摘要忠实或成本下降。[官方工程文章](https://www.anthropic.com/research/effective-context-engineering-for-ai-agents)。

从上述资料作出的设计判断：日常聊天可以让记忆自动工作，查看和纠错入口保留在次级位置。公开产品仍可能显示记忆通知，因此“完全不显示提示”是本项目的产品选择，不是所有主流Agent的统一做法。

## 建议改成怎样的体验

1. 顶部不再突出“记忆管理”，迁入账号菜单/设置。现有管理能力可继续作为查看、纠错、关闭和遗忘入口，暂不删除代码或已有条目。
2. 不要求用户填写短期/长期表单，不在每条回答下面固定展开记忆使用过程；详细调用及来源放开发审计，用户需要时再查看。
3. 通过自然语言表达偏好和更正：“以后先解释术语”“这次简短点”“以后别再按护理背景解释”。系统区分长期要求、本次覆盖和遗忘；只有确有必要时简短确认，不逐条追问是否保存。
4. 医学资料出处继续展示。减少记忆提示不会隐藏医学证据、来源故障或对象歧义。

## 内部需要补的三个环节

### 一、短期对话连贯性

保留现有带来源状态，在它旁边增加有限的近期完整交互和旧对话摘要：

`当前问题 + 当前有效状态 + 近期相关交互 + 必要旧摘要 + 相关长期记忆 + 本次医学证据`

这是上下文构成，不是执行权限优先级；系统边界与证据要求始终有效。当前用户明确更正覆盖旧要求，摘要、旧记忆和历史话题不能恢复已取消的限制。

近期片段需包含助手上一轮的组织线索，支持“第二点展开”等指代；历史助手文字只用于定位上一轮说了什么，不能直接当成已核验医学事实。涉及具体知识时仍重新查资料/核对版本与出处。不能把助手提到的疾病或病例写成用户自述。

首版可试保留最近2—3轮作为上限起点，但实际按相关性和字节/token预算选取，必须实测，不把固定轮数当通用标准。当前问题、有效更正、对象冲突为必需项，重复工具输出先去掉。

当旧历史接近给定额度，再对新增区间做增量摘要；保存覆盖消息ID、处理边界、话题、未决指代、有效更正、来源引用和版本。重置/遗忘后旧摘要失效或重建，不能重新灌回已清掉的内容。摘要失败应回退到近期片段与已验证状态，必要时澄清，不自动循环付费重试。

### 二、自动形成少量有用的长期记忆

先限定在低风险且明确自述的稳定信息：表达偏好、学习背景、持续学习目标。不是所有问过的主题都要记住，也不根据问诊问题推断身份或病史。

| 用户说法 | 建议处理 |
| --- | --- |
| “以后术语先解释一下” | 提取为长期表达偏好，保留原消息来源 |
| “这次只要一句话” | 当前问题覆盖，不改长期默认 |
| “我正在学护理，希望从基础讲” | 作为明确的学习背景/学习目标候选 |
| “如果患者有糖尿病……” | 假设案例，只保留在当前讨论，不建个人病史 |
| “我妈妈有高血压” | 不能归为本人；首版不自动长期保存健康自述 |
| “别再记我学护理这件事” | 停止使用对应条目、候选和摘要派生内容，旧事件不能重复写回 |

写入建议采用“先提候选，再由程序核验并提交”的内部流程。有限结构、原文来源跨度、用户角色和作用范围都验证通过才保存；不能让模型任意改写记忆库。更复杂表达先澄清或不写入，不靠大量关键词补丁宣称通用理解。

明确的更新/遗忘应立即生效；需要模型归纳的部分可按新增消息批处理，在不拖慢每轮问答的时点执行。建议先采用请求结束后的受控增量处理，队列/后台worker有实测需要再加入，不能把“后台任务”假定为不耗额度。设置每轮/会话提取和摘要调用上限、最大输入输出、usage记录及失败停止；避免每句都独立调用模型。

保留账号隔离、版本检查、来源消息、last_processed_message_id与失效标记。关闭自动记忆后停止新候选写入；关闭使用与忘记历史条目分别处理。用户可以查看/关闭，产品说明清楚自动记忆范围，聊天里不必反复提示。

### 三、按问题选择记忆并组装上下文

当前最多读取3种有限偏好，尚不需要向量检索。后续先按类型、话题、有效状态和时间选择；需要回忆某次历史讨论时再做独立受限查找。记忆应能回答“为什么与当前问题有关”，过时或冲突内容不能只靠相似度硬塞。

继续使用SQLite记录状态/摘要/记忆元数据；只有真实样本证明自由文本回忆检索不足，再评估Qdrant独立个人记忆collection，与公共医学文档分开。暂不引入额外记忆框架、数据库或多Agent。

上下文硬预算应覆盖系统提示、历史、摘要、证据和可选记忆，并预留模型输出；沿用字节上限作为保守保护，另用可靠的token计数/估算与实际usage校准，不能把当前24KB说成24000 tokens。压缩模型调用也纳入原请求时间/费用或另立明确后台预算。

## 实施顺序与验收

- **第一步：近期衔接与界面收敛。** 固定一组“展开刚才第二点/换病种/取消表格/不要沿用旧要求”样本，对比现版与加入近期交互后的方案。先让聊天自然，不以隐藏按钮代替能力改进。
- **第二步：自然语言形成有限长期记忆。** 扩展既有偏好存储的来源与处理边界，支持稳定偏好、临时覆盖和自然语言遗忘；把当前手动条目保留为高可信输入，不覆盖用户已有选择。
- **第三步：触发式摘要与可选历史回忆。** 长历史接近预算再压缩，检查重要更正、数字、人群、否定和来源是否丢失；以后再决定语义检索。

实施前固定对照场景和成功条件，开发与留出分开：正确接续、长期偏好是否该用才用、当次覆盖、跨账号隔离、忘记不复活、摘要忠实、旧助手内容不变成医学依据，以及延迟/输入用量/新增模型费用。先离线验证写入与失效，再小批真实模型验证；不以模拟检查数代替实际效果。

本建议尚未实施。26的手动记忆功能继续作为当前事实；下一轮若采用本方案，应另立代码/题集/用量快照，保留26及原RAG首轮结果。
