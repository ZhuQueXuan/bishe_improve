# 模块完成度与记忆冲突处理分析

日期：2026-10-24。目的：核对医疗项目已经完成的模块、剩余缺口和改进顺序，并为“当前输入与长期记忆不一致”建立讨论基础。本轮是分析与离线核查，没有改动业务实现或启用健康信息长期收集。

## 1. 整体判断

项目已经形成可运行的有限医疗资料问答闭环：知识图谱与专业文档检索、证据出处、受限多步任务、会话状态、上下文预算、有限跨会话偏好都已接入正式代码。

目前的主要短板集中在理解和验证：自然语言要求的作用范围、主体与时间变化、证据相关性、正文是否逐项得到来源支持，以及新版本的真实组合验收。不能将“接口已接通”“工程检查通过”直接等同于“复杂医疗对话已经可靠”。

本报告不使用完成百分比：项目没有冻结一个可计数的完整产品需求集合，报“80%完成”会掩盖有限实现与尚未验证的差别。

### 3.2 两个明确的要求作用范围问题

| 合成输入顺序 | 当前离线状态结果 | 分析 |
| --- | --- | --- |
| “糖尿病症状有哪些，这次用表格。”→“预防呢？” | 下一轮`format`仍为`table` | “这次”的作用范围没有记录，临时格式要求会延续；应该与篇幅的本轮覆盖统一处理 |
| “讨论糖尿病，只查预防，用表格。”→“换一个话题，介绍高血压。” | 对象已变高血压，但`field=prevent`、`format=table`仍保留 | 同义换话题没有清除旧要求；后续检索存在被旧“只查预防”限制的风险。此轮只验证状态，未实际运行检索答案 |
| 同上，第二条换成“换个话题，介绍高血压。” | 对象高血压，`field/format`均清空 | 说明问题来自有限字面规则，而不是所有换话题均失效 |

代码依据：`conversation_context.py`的`SessionMemory.ingest`主要依赖“换个话题”“只查预防”“用表格”等固定表达；没有给格式/字段设置turn或session作用域。现有351项通过，说明这些新表达未被已有断言覆盖，不能据此称现有测试失败或系统全坏。

### 3.3 与健康记忆讨论直接相关的边界

| 合成输入 | 当前状态或提取结果 | 能得到的结论 |
| --- | --- | --- |
| 历史“我之前感冒了。”；当前“感冒已经好了，我现在咳嗽。” | 讨论对象包含“咳嗽”“感冒”，状态为clarify | 当前对象提取没有表达“感冒事件已结束”；不能由此声称模型已经将旧病当现病，也不能声称已经正确处理康复 |
| “我妈妈有糖尿病。” | 讨论对象为糖尿病，没有主体字段 | 作为资料查询主题并不必然错误；但若未来直接将此状态写入个人健康库，就缺少区分本人/家属的依据 |
| “我没有糖尿病，我想了解高血压。” | 状态同时记录糖尿病/高血压 | 不能充分表达被否定对象与当前查询对象的区别；此处仅检查状态，没有验证最终HTTP是否澄清或模型如何回答 |
| 已存“详细”；当前“这次简短点。”；再下一次普通问题 | 本轮选择brief，下一轮恢复detailed | 篇幅已具备临时覆盖且不改长期默认的局部机制 |
| “我之前感冒了”“感冒已经好了”“我妈妈有糖尿病” | 三条长期偏好提取结果均为空 | 与当前限定范围一致。这不是通用健康语义分类器的完整验证 |

注意：`UserMemory.created_at/updated_at`是记录时间，不能自动代替健康事件发生时间；`active/paused/forgotten`是偏好条目状态，也不等于病情的“进行中/已结束/不确定”。

## 4. 建议的改进顺序

### 第一优先：统一要求作用范围，确定冲突规则

先让格式、字段、篇幅、解释方式共享清楚的作用范围：本轮、当前话题、当前会话、长期默认。新请求先判断是临时覆盖还是长期更新；换话题清除话题要求，不能只靠一个固定短语。

随后补主体、否定和时间变化的有限识别。第一步可以只用于当前会话，让“说的是谁、过去还是现在、是否已更正”可检查；健康信息是否跨会话保存，单独讨论后确定，不由本分析自动开启。

### 第二优先：减少不相关证据，补正文支持检查

按实际问题筛掉无关图谱食物/菜名，对图谱与文档共同分配证据预算。当前代码先保留图谱上下文，再将放得下的文档片段加入，存在图谱材料占用预算的倾向；本轮是代码分析，没有声称已经观察到文档被挤出的真实失败。

优先记录哪些主张有哪个原文支持，先人工核对少量回答及局部确定性规则，再决定是否值得加自动核验。对资料只给名称的场景，应继续明确说明不能展开。单纯增加引用数或知识库规模不会自动解决正文无依据的问题。

### 第三优先：做当前版本的小型组合验收

冻结新版本及题目后，覆盖“长期默认→本轮覆盖→下一轮恢复→换话题→原条目更正/忘记→继续追问”的完整路径。分别记录检索对象、输入实际选用记忆、证据、回答和用量；真实模型结果与离线替身结果分别保留。

RAG三模式继续使用相同问题和来源边界。已有测试题多为开发可见，新一轮要保留未参与改造的题；来源支持评分与医学适用性评价分别进行。是否追加真实外发试验及具体载荷，另按项目约定处理，本轮未执行。

上传管理页面、自动更新、大量资料扩展、个人记忆向量检索和更通用规划可后置；当前缺口不要求先引入新框架。

## 5. 当前输入与长期记忆冲突：建议先采用的原则

以下为待讨论设计，没有实施。

先分开三个动作：**这次回答采用什么、长期记录是否改变、旧记录是否仍保留**。三者不应绑定。例如这次简短回答，并不意味着以后都简短；记录用户说“已好了”，也不意味着删除其曾报告的事件。

判断顺序：主体是否相同→说的是不是同一件事/同一属性→时间是否相同→属于要求、用户自述还是专业资料→能否明确更新→是否影响本次回答。只有实质影响回答且无法自行判定时才澄清，不在每轮打断用户。

| 情况 | 本轮如何使用 | 长期记录如何处理（若该类信息已获准保存） |
| --- | --- | --- |
| 长期喜欢详细，本轮“这次简短点” | 用本轮要求 | 保留原长期默认，本轮结束后临时覆盖失效 |
| 长期喜欢详细，现在“以后都简短点” | 立即使用新默认 | 更新对应偏好，保留来源和版本；旧值不再作为有效默认 |
| 以前报告感冒，现在明确报告“那次感冒已经好了” | 不把那次事件当作当前进行中的状态 | 将同一事件标记为“用户报告已结束”，保留原发生记录及新来源；不将自述升级为医学确认 |
| 旧信息与新信息来自不同主体或不同时间 | 按各自主体/时间使用；不为本次问题无关的旧信息占用上下文 | 可并存，不能将家属信息覆盖本人，也不能把历史事件误当当前事实 |
| 以前明确某项健康限制，现在笼统说“没问题”，或只是询问相关知识 | 不能据此认定限制已经被撤销；有实际影响时作针对性澄清 | 标记待确认，保留冲突来源；不能仅按最新消息时间覆盖 |
| 用户要求按某个与检索资料不一致的医学说法回答 | 清楚区分用户说法与资料结论，不把用户要求当成专业证据 | 个人记忆不能改写知识库或替代来源核验 |
| 假设、引用、家属描述，或助手自己的推断 | 用于理解当前问题，不默认写为本人事实 | 不自动形成用户健康事实 |

对于“旧病会不会永远带入”的问题，还应区分保存与使用：过去事件即使保留，也只有与当前问题相关时才进入回答上下文；用户问历史时仍可按历史回溯。长期未提起不等于已康复，不能用固定天数自动宣告病情结束；可以让陈旧状态变为“当前情况不明/需确认”。

若后续确定保存有限健康事件，最小记录可包括：主体、事件类型、用户原话及消息来源、事件发生时间（未知则明确未知）、记录时间、当前状态、被哪条后续消息更正，以及适用范围。无需一开始建立完整电子病历或复杂个人知识图谱。

## 6. 下一轮可预先固定的验收例子

以下仅为建议场景，尚未实现新功能或获得通过结果：

1. 长期详细→本轮简短→下一轮恢复详细。
2. 长期详细→以后简短→跨会话仍简短。
3. 本轮用表格→下一轮不自动延续。
4. 同一换话题含义的多种常见表达，均停止旧话题限定。
5. “没有A，想了解B”只把B作为当前明确查询目标。
6. 本人和家属对同一病名的叙述不混写。
7. 过去事件→用户报告已结束→当前新事件，不将旧事件当进行中。
8. 过去与现在的数值/状态不互相覆盖历史。
9. 含糊否认重要旧信息时，按影响有针对性地澄清。
10. 假设、引用、助手推断不形成本人健康事实。
11. 遗忘或更正后，旧摘要、旧事件重放不重新激活失效内容。
12. 无关旧记忆不进入当前回答，相关历史可追溯来源；来源不足时不补造解释。
