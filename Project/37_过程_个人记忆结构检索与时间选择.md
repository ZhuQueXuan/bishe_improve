# D阶段：个人记忆结构检索与时间选择

日期：2026-10-26。承接[32持续框架](32_规划_分层记忆系统与逐模块实施框架.md)和[36受控保存](36_过程_受控长期疾病自述与跨会话使用.md)。本轮完成有限明确规则的结构/关键词选择、回顾与来源审计，已加载本机。按用户最新顺序，个人记忆和长对话的向量化仍在D—G全部完成之后另行评估。

## 1. 用户可见效果

登录且打开长期记忆使用开关后，可以询问：

| 输入示例 | 有限行为 |
| --- | --- |
| “你记得我保存过哪些情况吗？” | 本地回顾已确认、启用、来源可核验的本人疾病自述，附状态、时间原话、记录时间及原话；不调用图谱/回答模型 |
| “我之前保存的感冒是什么时候？” | 分别列出符合条件的事件，不把多次感冒合并；不是在判断今天是否患病 |
| “我2025年的感冒有什么资料？” | 可匹配在2026年说“去年”的事件，选定背景后仍按原医疗来源回答 |
| “我现在的感冒有什么资料？” | 过去感冒不会仅因同名被当作当前背景；未选入不表示没有相关疾病 |
| “你记得我已经好了的情况吗？” | 按已保存的用户报告结束状态回顾，不把“好转/不确定”当作已结束 |
| “我之前记住的那个病的预防资料是什么？” | 只有能唯一确定病名和事件时才补全检索问题；多条可能时先澄清 |
| “你记得我的回答偏好吗？” | 读取原三类已保存启用偏好，不掺入健康记录，不把回顾问题当新保存命令 |
| 一般知识、家属、假设或无关回忆 | 不把本人疾病自述随意带入；未知回忆类型请求具体说明 |

同账号的新聊天可回顾已保存记录。疾病保存方式仍按36：独立健康保存开关默认关闭，明确命令后需确认。此次没有扩大收集范围，家属/过敏原/药物/自由病历仍未接入。

## 2. 实现和开源取舍

新增纯规则模块`api/memory_retrieval.py`；`controlled_health.context_health`负责账号/状态/来源适配，调用纯选择器。原聊天APIView在工具前处理冲突和本地回顾；需要专业资料时仍由原ChatAgent工作。旧偏好接口与SQLite结构保持，无新表、依赖或迁移。

本轮核对了[LangMem检索工具源码](https://github.com/langchain-ai/langmem/blob/main/src/langmem/knowledge/tools.py)、[说明](https://github.com/langchain-ai/langmem/blob/main/README.md)及[MIT许可](https://github.com/langchain-ai/langmem/blob/main/LICENSE)，并复查[Mem0官方项目](https://github.com/mem0ai/mem0)；后者Apache-2.0及框架取舍见36。公开源码、问题和PR可查，但本轮没有独立保证这些项目的长期维护质量。LangMem工具面向LangGraph BaseStore，直接引入仍需重接本项目账号、来源、版本和权限；Mem0的广泛提取/检索也超出本轮有限只读选择。此次保留现有存储与A/B/C合同，实现项目特定的有限规则，不迁入框架，不启动其模型或向量能力。

本轮“关键词”指已知疾病名称、有限时间/状态词及明确个人指代。没有任意中文语义理解、病名同义词泛化、医学因果推断、BM25全文索引或个人向量召回。源数据仅C已支持的短结构事件，未扫描历史长对话。

## 3. 选择规则与时间

1. 服务端限定当前账号、active条目，未确认候选、停用或忘记条目不参与；再次核对实际用户消息、来源跨度和提取字段。使用开关关闭时不返回记录。
2. 明确区分个人背景问题、本地记忆回顾及一般知识问题。家属或其他人的问题不能借用本人记录；回顾偏好和回顾疾病分别处理，混合类型先澄清。
3. 先匹配病名、时间、状态和当前会话的明确范围。会话当次自述可覆盖当次背景，不写回长期库；不同时间的当前会话自述不能遮住明确询问的历史事件。无法证明同一次的同名矛盾先澄清。
4. 模型背景问题必须能确定相应事件；本地明确回顾可分别列举多个事件。最多选择5条，超出或超过原12KB必需状态预算时请用户缩小范围，不截断部分记录冒充完整结果。最终回答仍受原24KB完整messages预算约束。

不采用未经验证的“重要性+时间衰减”公式。当前长期健康条目为同一有限类型，先按资格与相关性过滤；记录时间只用于稳定展示顺序，不能让新消息自动覆盖旧事实，长期没被访问也不表示已康复。

有限日历规则支持“今天/昨天、本周/上周、本月/上个月、今年/去年/前年”和明确年月日。检索时分别将用户当前时间词和原消息时间词，以各自消息时间为锚点解释，使用当前中文项目的固定+08:00。原文及数据库event_time字段保持不变；不是通用日期规范化或用户时区系统。没有具体事件时间时，不用消息发送时间冒充事件发生时间。

例如2026年10月26日存的“去年”指2025年；2027年再问“去年”指2026年，不应因文字一样命中旧条目。只说明“去年”的事件也不足以证明发生在“去年12月”，应说明时间精度不足。周一问“上周”，可能同时包含某条“昨天”的独立事件；存在多次时不能静默选一条。

## 4. 已更新事件的时间来源

补正C的一处事件转换：用户明确选择原条目，报告由过去/当前变为已结束时，使用A的same_event_update决定；此前一律按correction会使部分过去→已结束更新被拒绝。A合同本身未修改，目标身份/版本/来源核验保持。

新原话“记住，我的感冒已经好了”可能没有重述“上周”。D允许从同一已确认事件的旧提交回执，提取最后一个可核验的事件时间，作为独立`event_time_reference`供查询使用。旧报告的状态不会成为当前状态，原报告字段也不被检索修改。

时间回溯最多检查20份同条目已提交的先前回执；遇到缺失/更改的中间来源就停止，不从更早旧材料绕过。新明确时间优先于此前时间。来源无法证明时宁可不选，不读取未确认候选，也不复活忘记条目。不是完整版本回滚或任意时间线系统。

## 5. 只读、来源与后续历史

回顾问题跳过原自然语言偏好写入器，防止“你记得我以前说以后详细回答吗”被错误保存成新详细偏好。实际回答仍按已保存简短值回顾；普通新偏好表达沿原路径处理。

回顾回答由本地有限模板生成，带原话、状态、事件时间和记录时间，明确是已确认用户自述。专业来源列表为空，不生成E证据编号。需要医疗资料的问题继续检索专业来源；个人记忆不是诊断或医学证据。

显式“已保存的那个病”得到唯一选择时，补全实际检索问题和回答问题，保持返回给用户的原query。普通非个人指代的原有接口约定保留，不能只在选择器里找到病名而仍向工具发送未解析的问题。

响应中`memory.selection`记录方法、选入ID/版本及原因、排除理由。排除理由不复制无关记录正文，其他账号记录不进入候选。本轮不新增长期检索日志表或逐次显示内部过程。

回顾用户问题及其助手回答不再进入后续对话引用，摘取缓存升级v7，避免忘记后旧回顾正文又被摘要带回。现有记忆版本/在途结果/暂停令牌规则保持；已测试本地回顾选取中发生版本变化会丢弃旧结果。工作记忆的完整个人背景快照与复杂暂停恢复组合仍按G完善，不声称本轮已完成通用任务记忆。
