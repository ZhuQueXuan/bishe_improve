# F阶段：记忆整理任务与遗忘来源闭环

日期：2026-10-26。承接[32阶段框架](32_规划_分层记忆系统与逐模块实施框架.md)和[38分层摘要](38_过程_分层原文摘要与预算一致性.md)。本轮完成有限整理任务、持久来源排除、归档和旧任务提交保护，已迁移并加载本机。个人向量仍在D—G之后，未提前接入。

## 1. 用户如何使用

登录，在“记忆设置”管理已保存内容：

- **停用**：保留条目，停止用于回答；明确启用后再使用。
- **归档**：保留原事件和状态，退出日常选取，表示用户要暂存这条旧记录。不会变成“已康复”；可在设置核对来源并明确启用。
- **忘记**：清空提取的长期条目内容，并持久排除可核验的原来源，清空账号派生缓存；原聊天仍保留。已忘记条目不能直接启用，用户发出新的明确请求并确认后可重新保存。
- **来源待核对**：来源缺失、变更或已被排除时，不能当作有效个人背景；整理将标记待核对，未核实前不能启用。
- **整理记忆（不删除聊天）**：执行一次有限本地整理，界面显示任务完成、失败、已过时或达到重试上限等实际状态。

归档与停用有不同的用户意图，首版都从日常读取中排除；尚未增加专用历史归档搜索。病情状态只按原C/B明确来源和确认流程变化，不因归档、记录年代或访问频率推断健康状态。

## 2. 整理内容与范围

新增`api/memory_lifecycle.py`、两个持久表`MemorySourceExclusion/MemoryMaintenanceTask`及偏好输入回执到消息的可空关联。旧账号、偏好和聊天接口保留。

本轮整理只执行四类操作：

1. 过期、个人版本旧、会话重置或来源失效的待确认健康候选标记expired，不接受旧确认；原处理回执仍保留防重放。
2. 已存疾病条目来源不能核验时标记invalid，停止正常读取；原内容仍供本人在设置核对，不等同忘记或原文删除。
3. 只有**同一事件身份、同一来源、同一完整语义记录**的活动重复条目才归档重复项；仅同病名、同状态、文字相似或不同来源均不自动合并。
4. 清空版本/会话/生成器不匹配、来源变更或被排除的摘要缓存；超过7天的可选派生缓存也可清空。原记录、聊天和健康事件不会因此过期。

每类最多检查50项；任一范围超过50时返回“需要缩小范围”，本次不做部分整理。当前管理页没有更细的分范围入口，超过该界限的账号需后续扩展，本轮不能称无限规模整理。长期没有被检索不会自动降权、康复、归档或忘记。C的健康非忘记条目上限保持50。

本轮没有普通聊天的后台健康提取，没有生成式归并、模型队列或向量删除任务。专业文档向量索引不受本轮影响。

## 3. 持久任务、版本与失败

任务有账号、稳定请求键、个人记忆版本、状态、尝试次数、60秒租约及结果。结果只保存计数/理由等最小信息，不保存健康原文；接口不暴露工作租约令牌。

设置按钮先创建或复用持久任务，然后在本次请求中执行有限工作，界面不假装已在后台完成。也提供`manage.py maintain_memory --user-id <明确账号ID>`处理这个账号最多3个已有待执行/可重试任务；不扫描所有账号，不自行创建任务。该入口可由未来项目内部调度调用，本轮未安装常驻worker、队列集群、Codex定时任务或自动唤醒。

任务领取在事务中检查状态/租约；未过期运行任务不能重复领取。进程中断后租约到期可以重试，同任务最多2次尝试；旧令牌不能提交新租约的结果。已完成任务重试返回原结果，不重新覆盖条目。

整理分为读取计划和事务提交。计划只包含ID、版本、动作和源状态指纹；提交时重新计算规范计划，同时核对任务租约和个人版本。用户在计划生成后忘记、修改、停用或改变相关来源，旧提交变成stale，不会恢复旧内容。不能通过修改计划动作绕过重新核验。

写入失败会回滚事务并保留failed状态，接口返回未完成；最多两次后停止重试。SQLite锁冲突也按失败处理，不宣称跨机器的分布式事务保证。明确的新整理请求可建立新任务，但不是对同一任务无限自动重试。

## 4. 遗忘来源与派生内容

健康条目忘记时，记录它的当前及此前**已确认**提交所关联的用户消息ID排除标记，不存一份健康原文。偏好输入从本版起直接关联正式落库用户消息；忘记时据该关联排除来源。旧偏好没有消息关联时，只在对应账号、对应会话中查找包含原source_text的字面用户消息（最多2000），不全库模糊查找；范围超过上限则请求明确处理，不虚报已完成。

排除记录只允许指向该账号的用户消息。构建有效会话历史时排除来源及紧随其后的助手引用，保留其他后续用户轮次。原聊天依旧可在聊天记录中查看，排除与删除是不同动作。为避免把已排除的末尾消息误认成并发新消息，历史返回额外保留原读取游标；不能重新查询最新游标而放过真正并发输入。

来源排除被候选确认和已存条目来源核验再次检查，不能只靠前端隐藏。摘要仍从过滤后的历史和有效来源重建，旧保存命令、回顾结果继续按C/D规则排除；更新/忘记同步清空账号缓存，原个人版本保护仍阻止旧在途结果返回。旧暂停任务的版本变化规则保持，整体工作记忆接线留G继续核对。

原回执、来源排除及已忘记条目身份保留防重放，不做物理批量删除。用户重新发送一条新的明确表达，可以按开关和确认流程重新保存；不会按同一段文字永久封禁。

边界：只排除已关联或有限字面核验的来源消息，不承诺“全历史里语义相似的所有健康表达一并抹除”。一条原消息同时含多个内容时，当前按整条来源及相关助手轮次退出记忆，可能一并排除其中其他背景；聊天原文保留。游客没有服务端账号级排除表，不承诺对所有旧游客令牌全局撤销。删除原聊天、备份文件物理清理和未来向量索引传播另行处理，未把它们说成已完成。

## 5. 开源方案取舍

核对了[LangMem后台整理说明](https://github.com/langchain-ai/langmem/blob/main/docs/docs/background_quickstart.md)、[概念设计](https://github.com/langchain-ai/langmem/blob/main/docs/docs/concepts/conceptual_guide.md)、[官方仓库](https://github.com/langchain-ai/langmem)，许可仍为此前核验的MIT。其后台提取/整理通常依赖模型及LangGraph存储，直接引入会扩大当前收集范围，并需重接本项目权限、版本、来源和费用约束。

本轮复用“热路径与维护分离、明确生命周期”的设计思路，使用现有Django事务和SQLite；不迁移框架或安装新服务。公开维护记录可查，但没有独立保证上游长期维护质量，也不把上游研究结果当作本项目效果。
