# 用户名或邮箱登录与注册校验

2026-10-27，用户反馈注册后无法重新登录，并确认登录时填写的是邮箱。修复作为本机工程版v1.0.2加载；用户现有账号、密码与聊天保留，不需要重新注册。

## 事实与原因

后端使用Django自带User及SQLite。数据库文件配置是后端目录内的`db.sqlite3`；以只读方式执行SELECT确认连接和auth_user表存在。服务日志显示此前注册201、自动登录200、创建会话201，之后重复登录401。因而现象不是“没有连接账号数据库”，而是原接口将输入原样当作用户名交给authenticate，完全没有邮箱解析。

用户当前登录框中的标识按只读计数核对：精确用户名匹配0、邮箱匹配1。没有读取/尝试用户的密码，没有公开其邮箱、用户名或密码哈希。最初数据库诊断中另有一组旧账号的邮箱重复，因此不能简单用`.first()`选一个账号。

核对成熟开源的[Django5.2认证实现](https://github.com/django/django/blob/stable/5.2.x/django/contrib/auth/backends.py)和[官方User/认证说明](https://docs.djangoproject.com/en/5.2/ref/contrib/auth/)，继续复用已有Django的密码哈希、authenticate、停用校验及Token，不引入新认证框架或改User模型，无数据库迁移。

## 变更

- 新增`account_credentials.py`解析标识。原精确用户名优先，兼容旧用户名；再处理周边空格/规范化，若没有用户名匹配，仅把唯一的大小写不敏感邮箱映射到原用户名。密码原样交给Django，绝不裁剪或自行比较哈希。
- 多个旧账号共用邮箱时拒绝邮箱登录，提示使用原注册用户名；不会在候选账号间试密码。邮箱形状的原用户名优先，密码不对不会跳到另一个人的同名邮箱。
- 新注册在原表内检查重复用户名/邮箱，邮箱忽略大小写；防止用户名冒用另一个账号的邮箱，或邮箱撞上已有邮箱形状的用户名。保留旧账号不合并不删除。字段类型/邮箱/用户名/长度在服务端验证，失败不生成半个用户；数据库故障与重复注册给不同错误。
- 登录/注册本来就是公开接口，现在明确不要求已有Token，以免浏览器残留失效Token在输入密码前就挡住它们。其他私有会话接口继续校验Token；新增检查证明无效Token仍被拒绝。
- 登录页改成“用户名或邮箱”，提供浏览器标准账号/密码自动填充属性。前端注册流程、Token存储和现有聊天隔离不改。注册用户名3—20字符/密码至少6位与原前端一致；本轮另限制密码1024和邮箱254字符、拒绝空白及不合法字段。没有新增邮件验证或密码找回流程。
