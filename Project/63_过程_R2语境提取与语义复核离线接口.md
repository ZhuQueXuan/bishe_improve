# R2语境提取与语义复核离线接口

2026年10月28日。承接[60调整方案](60_规划_自然语言记忆提取与跨会话闭环调整.md)、[61 R0范围](61_过程_R0首版范围与独立验收基线.md)及[62 R1硬校验](62_过程_R1新版候选合同与来源硬校验.md)，完成R2离线部分：语境提取请求、R1来源校验、语义复核请求及提供回复后的状态处理。新增41项检查，最终373项相关隔离回归通过，含原332项。

本模块没有模型SDK、传输执行器、数据库或回调，不会发出请求。测试传入的是人工构造的提取与复核回复；真实语言理解和提示效果尚未验收。正式应用仍为1.0.2/0005，新模块未接正式聊天或保存流程，本轮不迁移、重启或付费，不扫描真实聊天。

## 一 已实现的离线处理顺序

```text
受信R1来源快照和当前版本
  → 检查逐类收集与本环节处理许可
  → 准备只含必要语境的提取请求
  → 提供提取回复，严格解析和R1来源校验
  → 准备复核请求或保留单次偏好的未复核状态
  → 提供复核回复，核对每项判定、问题与覆盖检查
  → 输出不可写入的预览，等待R3政策与确认处理
```

新增`api/natural_memory_extraction.py`及对应测试，未改R1或旧P03模块。当前有三个主要入口：

| 入口 | 实际行为 |
| --- | --- |
| prepare_extraction | 校验来源和提取许可，构造有界messages与处理身份，不调用模型 |
| prepare_review | 重读同一来源并重验原提取回复，校验复核许可，构造复核messages，不调用模型 |
| preview | 只处理调用方已提供的回复，或返回下一步待处理请求；从不自动执行请求、确认或保存 |

疾病原词、肯定/否定、确定程度、原时间和关系继续使用R1合同，不加入新的病名或句式白名单。相邻语境中所有已纳入消息均保留给模型，包括选中引文之后的主体更正；来源不完整时返回needs_context，不裁剪后猜测。临时回答要求不会进入长期候选，原聊天要求的实际应用仍属后续接线，未以本轮接口通过代替组合验收。

## 二 提取合同区分无信息歧义和失败

提取提示版本为natural-memory-extraction-prompt-v1，实际回复合同为natural-memory-extraction-v1。五个根字段是contract、request_ref、outcome、items、clarifications：

| outcome | 允许内容 |
| --- | --- |
| propose | 有R1候选，没有澄清问题 |
| no_memory | 候选和问题均空；只是提取器的判断，还需覆盖复核 |
| clarify | 无候选，有具体澄清问题 |
| mixed | 有候选，也有待核对缺口 |

问题只包含reason、question和用户原话证据。原因限主体不明、指代不明、范围冲突、关系不明或语境缺口；问题正文仍是模型提议，需要后续复核是否必要、是否只问当前缺口。候选或问题的证据必须有当前用户依据，助手文字不能独立构造本人病史。

提示要求理解普通口语，保留不确定否定、跨句主体修正和时间限定；明确长期偏好与临时要求按字段分开，不因出现临时词整条丢弃。用户自述中引用自己的诊断单名称与外部例句引文要区分，不能恢复“出现引号一律拒绝”的规则。实际模型是否能做到这些仍待真实批次验证。

## 三 复核阅读全部语境并检查是否漏项

复核提示版本为natural-memory-review-prompt-v1，实际合同为natural-memory-review-v1。复核输入保留完整有界语境、所有结构候选及问题，不仅提供提取器选中的引文。

复核必须逐项覆盖提议，给出supported、contradicted或unclear，以及与判定一致的原因和真实用户引文。supported还必须引用候选曾使用的各个用户来源；助手语境不作为本人事实证据。原文唯一定位和原因枚举只能检查结构一致，不能代替自然语言含义是否正确的判断。

复核还要逐项评价问题为appropriate、unnecessary或unclear，并提交整体coverage为complete、possible_omission或unclear。覆盖回执必须列出全部已提供的来源别名，并给出当前用户证据；这只能证明回复绑定和形式完整，不证明模型实际理解无误。

即使提取items为空，也不能直接当成正确负例：复核若发现疑似漏项，转needs_reassessment，不用本地规则制造新事实或把补记算成模型召回。反驳原提议时保留原始提议及反驳原因，不自动把肯定改成否定、本人改成家属后再宣称成功。

### 普通偏好不默认追加第二次请求

纯表达偏好、新信息关系且没有澄清问题时，默认不准备第二次请求，结果为pending_review，明确标记extraction_only_not_supported。需要时可显式要求复核，但必须有对应环节许可。

这一分支仅提供成本控制接口，没有把单次提取升级为复核通过或自动保存。R3还需决定单次偏好提议如何进入确认或受控政策路径；相关自动模式需按R0标准独立评价，不能把pending_review计入直接自动成功。健康、空结果、混合输出、澄清及非新信息关系默认要求复核。

## 四 不同结果如何交给后续阶段

| 预览状态 | 含义 |
| --- | --- |
| awaiting_extraction / awaiting_review | 请求已准备，未提供相应回复；不表示已经执行 |
| pending_review | 单次偏好提议未获复核，等待后续决策 |
| proposed | 有获复核支持的提议，仍待R3/R4，不能写入 |
| needs_confirmation | 有证据不足的提议或被判必要的问题；具体确认流程待R3 |
| needs_reassessment | 覆盖不清、疑似漏项或问题不必要，不能作为澄清成功或无信息成功 |
| rejected | 提议被复核反驳，不改称正确空结果 |
| no_memory | 合法空提取与完整覆盖复核共同给出的判断，仍不是客观真值 |
| blocked | 对应许可关闭、许可类型/版本错误或未开启收集 |
| needs_context | 受信快照声明语境不完整，未准备模型载荷 |
| processing_failed | 坏JSON、过期回复、错引文、错误回执或预算失败；不冒称已记住 |

所有结果writable、writes_performed、user_confirmed、clinical_confirmation均为false，external_calls为0。得到复核支持后的semantic_assurance明确为review_model_judgment_not_proof，不能用两次模型同意替代真实效果验收或用户确认。R1内层结构包保留其原标志，R2复核单独记录，不篡改R1历史判断。

测试专门提供了一个两次人工回复都错误同意否定自述的场景：接口可以收到proposed，但仍不可写入，也不标医学确认。该场景说明双模型不能构成逻辑正确性保证，并非真实模型已发生该错误；健康初期候选确认及后续保留评价仍必要。

## 五 来源处理身份和许可边界

提供给模型的数据仅包括局部source_ref、role、content、recorded_at及已许可类别。账号、会话、数据库消息ID、服务器消息哈希、重置游标和来源排除等协议元数据不进入模型messages。正文仍可能含个人信息，因此未来外发仍需要按环节许可，不能以移除标识代替授权。

提取和复核许可是两个显式布尔字段，与来源许可版本匹配；旧auto_enabled或开启收集均不能代替云端处理许可。测试中的许可仅为虚构参数，没有写入任何真实开关。准备复核时仍会重验原提取及来源，不接受调用方直接声称“已经校验过”的中间包。

request_ref是服务器构造的本次不透明处理身份，绑定提示版本、完整来源及版本、处理许可；复核还绑定确切提取回复。回执必须与当前处理身份一致，不能仅凭item_1就把另一轮结果拿来用。它不是认证令牌或保存授权；真实消息和许可仍须R4落库重验。

完整messages字节预算包含提示、语境、候选及JSON包装，最多32768 UTF8字节；每次回复最多8192字节、候选最多5项。JSON禁止额外字段、重复键和非有限数，完全重复的追问直接拒绝，任一候选或复核项结构错误整批拒绝。缺少任何候选/问题的复核回执、重复回执编号、错引用、遗漏来源回执或伪造保存字段均不能通过。

1024输出tokens、45秒单调用、原90秒剩余期限及重试0以未来执行约束元数据保留；本阶段没有执行器，不声称已经通过实际超时、计费或SDK重试验证。重复构建纯请求不计为模型调用，也不能据此宣称调用预算控制已在线运行。
