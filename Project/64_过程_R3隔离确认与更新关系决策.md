## 一 本轮范围及保留、替换边界

新增[natural_memory_policy.py](../bishe/knowledge_graph_backend/api/natural_memory_policy.py)、[测试](../bishe/knowledge_graph_backend/api/test_natural_memory_policy.py)和[R3合同](../bishe/data/natural_memory_v1/r3_policy_contract.json)，继续复用R1原话定位与完整语境绑定，以及R2提取、复核回复校验。R3必须从原始回复重算R2结果，不能接受客户端自称“已经复核”的预览包。没有新增病名词表或固定自然语言句式。

| 机制 | 本轮处理 |
| --- | --- |
| 账号、逐类许可、来源、会话版本 | 保留并在确认前重查；来源按数据库消息标识精确取回的虚构信封比较，不扫描历史 |
| 旧正式提取、P02保存及页面 | 原样保留；旧固定句式仍在旧正式路径，新模块没有被业务调用 |
| 模型提议直接视为确认、按最新插入覆盖 | 新路径不采用；健康必须有明确用户确认，关系不清先核对 |
| 旧确认按钮只绑定候选内容 | 新路径绑定展示摘要、来源、完整政策、全局决策版本、目标版本及目标完整摘要 |
| 实际事务、磁盘幂等、HTTP鉴权 | 本轮只给出待提交状态，R4再接持久化和真实入口；不宣称内存版本检查等同数据库并发安全 |

本模块假定账号身份、实时来源、许可、会话版本、最新用户消息及用户的明确操作意图由受信服务端提供。哈希用于发现内容变化，不是身份签名；模型不能提供这些权威字段。返回的完整状态供内部持久化适配，不能原样当作公开接口返回。

## 二 确认和澄清

本人疾病自述始终先确认。用户确认“保存这条怀疑”后，`certainty=possible`仍保留，`clinical_confirmation`始终为否。否定方向和确定程度分别保存，不因为用户确认升级为确诊，也不从测量正常推断疾病消失。

点击确认必须对应当前展示，期间没有更新的用户消息。明确回复必须来自同一账号、同一会话的最新用户消息，消息顺序和时间合法，且绑定所回答的展示。一次点击或一次明确回复即可完成已展示候选的确认。

主体、范围或关系未解决时，普通“接受”不能补齐缺口。`resolve`允许一次有针对性的回复结束原问题：重查旧展示及新语境，新回复须带入旧语境并通过R1/R2；断言保持不变时可确认已解决的关系，明确属于临时要求且复核得到无记忆结果时可直接结束核对、保留旧默认。如果疾病或原断言变了，需要重新展示，不通过澄清顺带保存新事实。

本轮“明确回复”和“同一次”等含义来自测试中人工构造的受信意图，程序没有按这些中文词语匹配，也没有真实模型识别器。真实聊天能否正确生成这些意图，仍需后续接线和独立语义验收。不能把57项离线检查称作自然语言确认成功率。

偏好默认也进入待确认。只有“偏好自动开关”和“该类真实语义门槛通过”两个受信标记同时成立，新偏好槽才允许推演自动接受；换长期默认仍需确认。这个分支仅在虚构状态中测试，正式开关未开启。R2跳过二次复核的偏好会保留“仅提取、未复核”标记，不伪装成双模型支持。

## 三 更新关系与冲突

| 关系 | 决策与验收结果 |
| --- | --- |
| 新信息 | 无同属性记录时可展示；本人健康确认后才进入可用资格 |
| 重复信息 | 必须明确为同事件；合并来源、保留原确认和旧版本，不新增事件记录 |
| 补充 | 可补原来缺失的时间和来源；不能借“补充”改变肯定否定、确定程度或替换已有明确时间 |
| 同事件状态变化 | 绑定指定事件与版本，保留事件标识和旧版本；未提供的新时间不清空旧时间 |
| 新事件 | 明确选择后建立独立事件，不覆盖旧事件；不按入库时间判断哪个历史事件才是真实 |
| 更正 | 必须指定旧目标与版本；不同病名也可更正，但模型的关系字段不能自行选择目标 |
| 新默认 | 同偏好槽位在确认后替换，保留旧版本；临时详细回答不改变长期简短默认 |
| 撤回、暂停、保留原项 | 撤回或暂停后停止作为背景；有争议的旧项只在用户明确保留后恢复，拒绝新候选不会自动恢复它 |

同属性的关键矛盾先把旧项标为有争议，解决前不给当前背景资格。复核判为主体错误时，可先隔离匹配的旧本人记录；明确撤回再结束错误归属，不新增家属条目。同一批多个同属性候选也不能靠插入顺序同时成为当前事实，除非各项有明确的新事件选择。

`resolved`是R3的受信事件操作，保留“用户报告本次已好转”的事件状态，不把原疾病自述改成“从未有病”。R1候选合同没有被偷偷扩充为模型自动识别康复；本轮只验证人工指定该操作后的版本与使用资格行为。按问题选择历史还是当前事件、回答如何限定含义交R5。

## 四 失效、遗忘与失败边界

确认时重查原始信封全文摘要、账号/会话、政策摘要、会话重置版本、最新用户消息、展示摘要、全局状态版本及目标版本/摘要。原话编辑、来源消失、许可变化、两个窗口使用旧版本，均拒绝旧操作。新的处理批次即使返回空或处理失败，也会替换旧的待确认展示；管理操作会清除旧展示。

遗忘清除目标的全部提取正文、历史版本、来源引文和确认内容，并清空待确认计划。所有曾链接的语境消息及确认消息标识保守列入排除表，防止旧来源换个请求键重新提交。保守排除可能同时使使用该语境的其他记录暂时不合资格；精细按字段裁剪不在本轮实施。原始聊天信封保持。新的明确来源可以重新建立候选，旧来源仍排除。

幂等回执只存摘要和版本。同键同输入重放只返回“已处理”的元数据，不重做状态变化，也不重复宣称已保存；同键不同输入拒绝。遗忘后重放旧确认不能复活内容。暂停、撤回、遗忘仍允许在关闭收集后执行。

每次操作复制输入状态后决策，第二项失败不会把第一项修改留给调用者；这是纯函数层的整体失败保证。上限为50条记录、每条20历史版本、128回执、512排除标识和1MiB状态，超限拒绝，不截断。一次定向回复内部完成暂存和确认，最终版本推进两次；R4必须把整个返回状态作为一个原子提交，仍以最初预期版本进行CAS，不能拆开保存中间计划。

旧回答、检索缓存和暂停任务检查点的实际失效尚未实现，交R6；本轮“迟到结果”只验证决策/确认/旧来源不能恢复记忆，不宣称已拦截在线回答展示。
